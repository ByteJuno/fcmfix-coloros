# 工作原理

ColorOS 在哪些位置限制 FCM，模块改了什么。每个 Hook 点的固件依据见[固件核对记录](firmware-notes.md)。

## ColorOS 在哪里拦截

正常的 FCM 链路：

```text
应用服务器 → Google FCM → Google Play 服务（GMS）→ FCM 广播 → 目标应用 → 系统通知
```

国行 ColorOS 16 / 17 可能在这些位置限制它：

- 电池组件把 GMS、Play 商店等 Google 核心包设为禁止全部联网；
- 系统拒绝启动没有进程或处于 stopped 状态的应用；
- 应用分类、自启动、GCM bind、Hans 冻结和代理唤醒策略继续拦截；
- FCM 拉起目标应用后，后台网络控制在数秒内重新冻结它并关闭 socket，应用来不及拉取消息正文；
- 国行配置缺少国际版中的部分 GMS Doze 白名单条目；
- ColorOS 17 在 Google 连通性探测失败后，把 GMS 的唤醒闹钟降级、把 Google 应用放入受限待机分组，熄屏后 FCM 心跳与重连停止。

典型表现：应用打开时能收到通知，划掉后收不到；日志出现 `Failed to broadcast to stopped app`；消息积压到亮屏或打开应用才出现。

## 模块做了什么

### 系统框架作用域

- 核验 GMS 真实 UID、精确的 FCM action 和明确目标后，为放行的应用补充 `FLAG_INCLUDE_STOPPED_PACKAGES`，让广播到达已停止的应用；
- 只对放行的目标应用绕过应用分类、自启动、GCM bind、service 启动、冷启动拦截、云控名单和关联启动限制，并解除必要的冻结和代理限制；
- 每次有效 FCM 到达后，只为目标 UID 建立 20 秒投递窗口：暂时阻止 Hans 重新冻结、Osense 广播代理和 `OAppNetControlService` 关闭 socket，
  不拦截目标的后台作业；窗口结束后恢复系统原有的省电策略；
- 为 GMS、GSF 和 Play 商店补充缺失的 Doze 条目，保留 ColorOS 原有白名单；
- 让系统始终认为 GMS 不受限，避免 GMS/GSF 的唤醒锁被丢弃、闹钟被降级，或前台应用唤醒 GMS 被限制；
- 熄屏弱信号和深度睡眠按应用断网时放行 GMS，GMS 的闹钟不再等待网络恢复；网络恢复后再发一次重连请求，并跳过恢复时对 GMS 的强制停止。整机断网无法阻止；
- 电池组件声明 `IgnoreGmsUserSet=true` 时，丢弃系统针对 Google 核心包下发的禁网规则，不依赖电池作用域。这一层分不清规则来自电池组件还是流量管理，
  所以没有这一声明的系统上不生效，用户手动设置的联网权限保持不变；
- 可选阻止系统在应用停止时自动删除它已有的通知。

### 电池作用域

电池组件运行在 `com.oplus.athena` 进程中。模块在这里做三件事：

- 把针对 Google 核心 UID 的 `POLICY_REJECT_ALL` 写入改为 `POLICY_NONE`。不直接修改流量管理进程中的规则；如果某个 OTA 把手动设置也转交电池进程，
  需要针对该固件复查；
- 把 `oplus.intent.action.google_restrict_change` 广播中的 `restrict_enable=true` 改为 `false`，名单更新照常下发；
- 电池组件声明忽略用户设置时，把旧的“用户改过”标记视为未设置，让电池组件重新接管这些包
  （见[流量管理里没有 Google 入口](report-issue.md#流量管理里没有-google-入口)）。

下发深度睡眠联网白名单前，也在这里补入 GMS，兼容 ColorOS 16 的名单构造方式。

## 适用环境

ColorOS 17 `PLK110_17.0.0.102(CN01)` 按全量包核对了全部 Hook 点，ColorOS 16 `PLK110_16.0.10.500(CN01)` 做过严格的强停实测。
其他机型或后续 OTA 可能可用，但没有经过同等级验证。Hook 与固件不匹配时会记录 `hook error` 或 `Unsupported`，并保持系统原行为。

## 与上游的区别

| | [kooritea/fcmfix](https://github.com/kooritea/fcmfix) | FCMFix ColorOS |
| --- | --- | --- |
| 目标系统 | Android 10–15 通用，附加 MIUI / HyperOS 适配 | 国行 ColorOS 16 / 17，已移除 MIUI / HyperOS 功能 |
| 作用域 | 系统框架；MIUI / HyperOS 可选“电量和性能” | 系统框架 + 电池 |
| 包名 | `com.kooritea.fcmfix` | `io.github.artifical0.fcmfix.coloros`，可与上游同时安装，但不要同时启用 |
| FCM 广播 | 唤醒已停止的应用 | 同时只放行来自真实 GMS 的广播 |
| ColorOS 后台限制 | 自启动、广播代理、唤醒锁代理、GMS 受限状态 | 另外处理应用分类、bind / service、冷启动、云控名单、关联启动，以及推送后的二次冻结和断网 |
| Google 核心服务联网 | 不处理 | 阻止禁网、闹钟降级和受限待机分组，补 Doze 白名单，深度睡眠时保持联网 |
| 应用界面 | 允许列表与选项 | 状态、应用、时间线三页，含自查和导出报告 |

## 配置

放行列表通过 LSPosed 远程配置提供给 Hook，Android 14 及以上通过带发送方身份的广播即时刷新，更早的系统保存后需要重启。

放行规则：手动打开的应用，加上开启自动放行时扫描到的 FCM 应用中未被排除的部分。自动放行在读取配置时扫描一次声明了 FCM 接收组件的应用，
之后只在应用安装、更新、组件变化和卸载时重新检查该应用，推送路径上只查已扫描好的集合。系统包（UID 小于 10000）不参与自动放行。

## 自查与时间线

“状态”页向系统框架发送带身份的查询广播，系统框架在独立线程中只读地收集配置、GMS 联网策略、待机分组、Doze 白名单，以及每个放行应用的状态。
推送时间和次数只保存在系统框架内存中（最多 256 个应用，重启清空）。某一项在当前固件上读取失败时显示“未知”，不影响推送。

FCM 连接由 netlink `sock_diag` 每分钟采样一次（系统框架不能读 `/proc/net/tcp`）：

- GMS 到 5228–5230 端口的连接算作 FCM 连接。443 连接只有远端地址在这些端口上见过，或是 `mtalk.google.com` 当前的解析结果时才算；
- 连接在但发出的数据连续重传 3 次以上没有回应，或累计 30 分钟（不计休眠）没有收到数据时，显示“无响应”；
- 两次采样之间连接被取代记为“重连”，一条连接也没有记为“断线”，再次看到时记为“恢复连接”。断线时长按采样估计，可能偏长。

“时间线”页还记录亮灭屏、深度 Doze、默认网络切换和推送，连接与系统事件最多 300 条，推送最多 150 条。采样不会唤醒设备。

“导出完整报告”用 Root 运行打包在 APK 中的 [`collect-report.sh`](../scripts/collect-report.sh)，只读取状态和日志，并附上自查结果和模块保留在内存中的最近 1000 条日志。
有些机型的 logcat 只能保留几分钟，这部分日志不受影响。
